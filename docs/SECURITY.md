# Cloud security, CSPM, SSO, load balancing and HPC (Units 4 and 5)

This document maps the syllabus topics of Units 4 and 5 to what the project actually implements. Use it as the source for the report sections.

## Shared responsibility

| Layer | Who secures it | Examples here |
|---|---|---|
| Physical data centre, hardware, network edge, TLS certificates | Cloud provider (Render) | HTTPS on the public URL, platform load balancer |
| Container build, application code, dependencies | Us | Non-root Docker user, bandit and pip-audit in CI |
| Identity and access | Us | Google single sign-on, domain allow-list |
| Data | Us | In-memory processing only, opt-in AI sharing |

## Threat model

| Threat | Control in this project |
|---|---|
| Oversized or malformed uploads (denial of service) | 20 MB limit, PDF magic-byte check, 40 page cap, corrupt files rejected with 422, per-check error isolation |
| Resource exhaustion by many users | Per-client rate limit, concurrency limit with 503 and Retry-After, audit timeout |
| Server-side request forgery through links in PDFs | Links are never fetched, liveness is reported as Cannot Tell |
| Cross-site scripting from text inside a PDF | Frontend renders with textContent only, Content Security Policy (scripts only from the same origin; inline styles are allowed because the CSS lives inside index.html) |
| Clickjacking and content sniffing | X-Frame-Options DENY, frame-ancestors none, nosniff |
| Session theft | Signed cookie, HttpOnly, SameSite lax, Secure flag in production, HTTPS only |
| Unauthorized use | Single sign-on gate on the API and the status endpoints |
| Leaking user documents to a third party | Files never stored, AI sharing only when the user ticks the option and a key exists |
| Secret leakage | Secrets only in environment variables, none in the repository, session key generated by Render |
| Vulnerable dependencies and insecure code | pip-audit and bandit run in CI before any deploy |

## Cloud Security Posture Management (CSPM)

CSPM means continuously checking cloud configuration against a security baseline and reporting drift with remediation advice. Enterprise tools such as AWS Security Hub, Microsoft Defender for Cloud and Prisma Cloud do this for whole cloud accounts.

What this project provides, at application level:

- `GET /api/posture` evaluates the running deployment against ten checks: TLS in transit, security headers, SSO enabled, SSO domain restriction, session secret strength, rate limiting, upload limits, non-root process, API docs hidden in production, data retention and AI consent. Each result has a status and a fix. The page `/status.html` shows the score.
- Shift-left scanning in the pipeline: bandit (static analysis) and pip-audit (known vulnerable dependencies) must pass before deploy.

Limitation to state honestly in the report: Render does not expose cloud account resources to scan, so this is application and pipeline posture, not account-wide CSPM.

## Single Sign-On (SSO)

- Protocol: OpenID Connect authorization code flow with Google as the identity provider.
- After login the server checks that the email is verified and, if `SSO_ALLOWED_DOMAINS` is set, that the domain is allowed.
- The session is a signed cookie, so it is stateless and works across load-balanced instances as long as they share `SESSION_SECRET`.
- When SSO is not configured the app runs in open demo mode, and the posture page reports it as a warning.

## Load balancing (Unit 5)

- On Render the platform load balancer sits in front of the service. The free plan runs one instance, and multiple instances need a paid plan as far as I know.
- To show the concept, `docker-compose.yml` and `deploy/nginx.conf` run three app instances behind nginx with round robin, passive health checks (`max_fails`, `fail_timeout`) and retry on failure. Other algorithms are one line away: `least_conn` and `ip_hash`.
- Each response carries `X-Served-By` so you can see which instance answered.
- Measured result, three real uvicorn instances behind a real nginx on one machine (see docs/EVIDENCE.md): requests split evenly, a killed instance caused no failed requests, and the instance rejoined the pool after the 10 second fail timeout.

## Resource utilization (Unit 5)

- `GET /api/metrics` reports CPU percent, process and system memory, load average, in-flight requests, completed audits, errors, rejected requests and p50 and p95 audit latency, per instance.
- A semaphore limits concurrent audits. When the server is saturated it sheds load with 503 and Retry-After instead of crashing.
- A performance fix found while testing: colour contrast checking took 20 seconds on a 40 page document and is now under 2 seconds, which matters on a small free instance.

## High performance computing on cloud (Unit 5) and parallelization (Unit 3)

- `POST /api/audit-batch` audits up to five PDFs in parallel using a process pool (data parallelism, one document per worker).
- `scripts/benchmark_parallel.py` measures sequential versus 2 and 4 workers and prints speedup and efficiency.
- The sandbox used to build this had one CPU, so no speedup could be measured there. Run the script on your own machine and put the table in the report. Expect efficiency below 100 percent because of process start-up, data copying and the serial parts of each audit (Amdahl's law).

## Known limitations

- SSO needs a Google OAuth client, which has to be created by the account owner. It was tested with mocks, not against live Google.
- The posture checks describe this application, not the whole cloud account.
- The in-memory rate limiter is per instance, so with several instances the effective limit multiplies. A shared store such as Redis would fix that.
- A request that times out stops waiting but the worker thread finishes in the background.
